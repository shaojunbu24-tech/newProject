# 电力设备多模态标注规则 1.2

## 1. 目标

1.2以结构化JSON作为唯一事实源，支持以下输出：

- 设备、部件和缺陷识别训练数据；
- 单图中文描述和多模态提示词；
- 参考图—修改文本—目标图组合检索数据；
- 配电架空线路六层知识标注；
- 输电、变电、配电、发电等领域扩展；
- 自动校验、人工复核和标签版本管理。

1.2不允许模型自由创造设备、部件或缺陷标签。所有正式标签必须来自`标签候选树1.2.json`。候选树之外的内容只能暂记为“其他待复核”，经专家审批并加入新版本台账后才能参与训练。

## 2. 核心流程

```text
原始图像与文件名
  ↓
阶段一：图像路由
  业务域 → 设施场景 → 拍摄任务 → 适用标签包
  ↓
阶段二：设备主题分层标注
  设施/线路 → 主设备 → 部件 → 子部件 → 静态属性
  ↓
阶段三：缺陷标注
  根据载体类型加载缺陷候选 → 绑定载体 → 记录可见证据
  ↓
阶段四：自动校验
  结构、台账、关系、证据、完整性、跨字段逻辑
  ↓
派生输出
  纯视觉描述、业务描述、检索描述、组合检索修改文本
```

## 3. 业务域和设备类别必须分开

业务域描述设备所处的生产业务场景，设备类别描述图中对象是什么。不能因为对象是变压器，就一律把业务域标成“变电”。

例如：

```text
10kV线路杆号 + 杆上配电台区 + 三相变压器
→ 业务域：配电
→ 设施场景：配电架空线路
→ 设备类别：配电变压器

500kV变电站 + 2号主变 + 散热器
→ 业务域：变电
→ 设施场景：户外变电站
→ 设备类别：主变压器
```

文件名可以帮助判断业务域、站线名称和设备编号，但必须记录信息来源；图像无法验证的信息不能伪装成视觉结论。

## 4. 阶段一：图像路由

### 4.1 固定路由顺序

1. 从固定候选中选择业务域；
2. 只加载该业务域允许的设施场景；
3. 选择拍摄任务和拍摄范围；
4. 判断图像质量和可继续标注状态；
5. 激活相应领域标签包。

### 4.2 路由候选

- 业务域：发电、输电、变电、配电、用电、跨领域、无法判定；
- 拍摄任务：设备识别、缺陷巡视、状态核查、表计读取、铭牌采集、红外测温、通道巡视、其他待复核；
- 拍摄范围：场站全景、线路通道、杆塔全景、杆塔塔顶、杆塔塔头、杆塔塔身、杆塔塔基、设备全景、设备部件近景、缺陷特写、铭牌图、表计图、红外图、非标准图；
- 路由状态：可以、部分可以、需要人工路由、无效图像。

### 4.3 来源优先级

```text
人工确认 > 设备台账/工单 > 图像可见证据 > 文件名解析 > 模型推测
```

“模型推测”不得单独生成正式站点、线路、杆号、相位和严重等级。

## 5. 阶段二：树形设备主题标注

### 5.1 对象层级与JSON保存方式

```text
业务域
└── 设施场景
    └── 设施或线路实例
        └── 设备实例
            └── 部件实例
                └── 子部件实例
                    └── 缺陷或状态量
```

1.2的权威JSON必须使用嵌套的`标注对象树`保存上述包含关系，不再把`设施实例`、`设备实例`、`部件实例`和`缺陷实例`作为互相并列的顶层数组：

```json
{
  "标注对象树": [
    {
      "对象类型": "设施",
      "对象编号": "设施01",
      "设备实例": [
        {
          "对象类型": "设备",
          "对象编号": "设备01",
          "部件实例": [
            {
              "对象类型": "部件",
              "对象编号": "部件01",
              "缺陷实例": []
            }
          ],
          "缺陷实例": []
        }
      ]
    }
  ]
}
```

包含关系由JSON嵌套位置表达，不再重复保存“部件01属于设备01”或“缺陷01位于部件01”等关系。只有邻近、连接、跨对象影响等非包含关系才写入可选的`关联关系`。

每张图必须指定一个`主要对象主题`；它可以是设施、设备或部件。允许多个次要设备。每个设备、部件和子部件必须保存标签代码、中文名称和候选树路径。

### 5.2 选择规则

- 主设备：一张图至少一个；无有效设备时应在路由阶段判为无效或待人工路由；
- 部件：零到多个，只标达到清晰度和尺寸要求的可见部件；
- 子部件：仅在缺陷定位、检索或业务规则需要时标注；
- 同类多实例：逐实例标注，不能只写数量后省略实例；
- 虚标签：不得直接标注，由实标签自动合并生成；
- 辅助标签：只用于过滤、废弃、非目标等业务逻辑；
- 候选外对象：正式标签只能选`OTHER_REVIEW/其他待复核`，并在`候选外描述`中记录原词。

层级例外：配电线路的绝缘子、导线和金具直接属于杆塔或线路设施，可以直接放在设施节点的`部件实例`中；仅拍到表计等部件特写、父设备未进入画面时，也允许把该部件直接放入设施节点，并记录“父设备图外未实例化”，不得虚构一个不可见设备。

表计、开关分合状态、油位和温度等观测任务写入`状态量标注`，不应为了填充缺陷字段而把一次正常读数标成缺陷。读数无法稳定辨认时记录“不可判定”，保留原图供人工复核。

### 5.3 配电架空线路六层知识

PDF中的六层知识保留为配电架空线路标签包，但不在JSON中复制保存两套标签结果：

| 六层任务 | 1.2结果位置 |
|---|---|
| 拍摄位置 | `图像路由.拍摄范围` |
| 杆塔 | `标注对象树`中的杆塔设施节点及其`属性` |
| 杆上设备 | 杆塔设施节点中的`设备实例` |
| 杆塔元件 | 杆塔设施节点中的`部件实例` |
| 运行环境 | `环境标注` |
| 缺陷隐患 | 缺陷载体节点内部的`缺陷实例` |

`知识层任务状态`只保存完成状态和对象编号引用，不重复保存标签值。

## 6. 阶段三：缺陷标注

### 6.1 缺陷候选生成

```text
当前业务域
∩ 当前设施场景
∩ 当前载体设备/部件允许的缺陷
∩ 当前启用版本
= 本次缺陷候选集合
```

例如识别到“主变压器—散热器连接管接头”后，开放渗漏油、油污痕迹、腐蚀、松动、破损和无明显异常等候选；不开放鸟巢、绝缘子伞裙破损等无关候选。

### 6.2 缺陷必填关系

每个缺陷必须包含：

- 固定候选中的缺陷代码和中文名称；
- 缺陷所在对象编号；
- 视觉判定状态；
- 直接可见证据；
- 置信度或复核要求；
- 缺陷框或无法画框的原因。

文件名中的“雷击、渗漏油、一般、严重”等只能作为外部先验。若图像只显示焦斑或油污，应优先标注视觉现象，将故障原因或业务等级列为待复核。

### 6.3 无缺陷和不可判定

- `已完成无目标`：已经检查，未发现候选缺陷；
- `属性不可判定`：目标可见但证据不足；
- `本图不可见`：载体或检查部位未进入画面；
- `未处理`：任务尚未执行，禁止进入训练。

## 7. 阶段四：自动校验

必须依次执行：

1. JSON结构校验：必填字段、枚举、坐标和类型；
2. 标签台账校验：代码存在、名称匹配、版本启用、标签性质正确；
3. 路径校验：设备属于当前场景，部件属于当前设备；
4. 对象关系校验：设备、部件和缺陷位于允许的父节点中，编号全树唯一；
5. 视觉证据校验：缺陷至少一条直接证据，原因推断与视觉事实分开；
6. 完整性校验：所有适用阶段或知识层都有完成状态；
7. 业务规则校验：虚标签不能直接标、背景杆塔过滤、候选外标签不能进入训练；
8. 数据划分校验：同一线路、杆塔、设备或巡检事件不得跨训练/验证/测试集。

配电架空标注框质检可参考文档使用IoU不低于0.85；多人抽检一致性目标为Krippendorff α大于0.8。

## 8. JSON转描述文本

所有文本必须从审核通过的结构化字段派生：

- 主体描述：主要设备主题或主要部件；
- 属性描述：拍摄范围、部件、位置、外观和状态；
- 纯视觉完整描述：只使用图像证据；
- 业务完整描述：可加入文件名、台账或工单信息，但注明来源；
- 简短检索描述：设备＋部件＋可见异常；
- 组合检索修改文本：保持项＋变化项＋目标状态。

禁止把`不确定信息`写成肯定结论；禁止直接用文件名覆盖视觉结果。

## 9. 版本和扩展

- 标签代码一经进入模型训练原则上不修改；
- 中文展示名可以通过映射调整；
- 新标签先进入候选申请，经专家审核后在新版本启用；
- 发电、输电、变电、配电分别维护领域标签包；
- `标签候选树1.2.json`是当前1.2起始台账，不宣称已经穷尽全部电力专业设备；
- PDF中的“188类”和各层标题合计“194类”存在口径差异，正式导入前应按实标签、启用状态和参与训练状态重新核数。

候选覆盖情况和严格使用边界以`标签候选树1.2.json`为准；修改候选树后必须执行1.2 Skill中的`validate_resources.py`。

数据库、目标检测训练或统计需要扁平表时，应从`标注对象树`生成派生视图，例如`设备表`、`部件表`和`缺陷表`；派生结果不是第二份人工标注，不得反向形成两个事实源。

## 10. Skill化接口

后续可将本目录封装为`power-image-annotation-v1-2` Skill：

```text
power-image-annotation-v1-2/
├── SKILL.md
├── agents/openai.yaml
├── references/
│   ├── 标注规则1.2.md
│   └── 标签候选树1.2.json
├── assets/
│   └── 标注规则1.2.json
└── scripts/
    ├── validate_annotation.py
    ├── select_candidates.py
    ├── render_captions.py
    └── build_structured_triplets.py
```

1.2 Skill允许一次读取与当前任务有关的完整标签包，并在一次模型调用中完成路由、对象树和缺陷初标。四阶段仍是结果组织和校验顺序，不强制拆成多次模型调用，也不强制保存逐层候选快照。2.0继续承担严格渐进披露和双阶段门禁流程。
